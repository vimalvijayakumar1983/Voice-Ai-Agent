# Recovery transport canary and remaining recognition delay

## Scope and safety

Runtime candidate `1656251` introduces an explicit opt-in profile flag,
`knowledge_repair_transport_enabled: true`. Default is OFF. The candidate creates
one tenant/call-scoped OpenAI HTTP client after the greeting's first audio frame.
One bounded models-list read prepares transport; no speculative completion,
dummy speech, new LLM pass or answer is generated by preparation. Models-list
permission/network failures fall back to the original path without blocking a
caller turn. Normal recovery still has its original model, prompt, validation,
token accounting, no-retry policy and two-second deadline.

Credentials are loaded again for each real recovery attempt. The prepared client
is used only if the current credential matches. Clients and credentials are never
shared across calls or tenants; shutdown cancels preparation and closes the client.
Only status, preparation duration and client-use count are exposed in diagnostics.
A reused client does not prove an upstream server retained its TCP connection.

## Preliminary isolated recovery experiment

Six synthetic repair requests, same model/prompt/settings, three paired questions;
order reversed in the middle pair. These are not call latency measurements.

| Synthetic request | Fresh client ms | Prepared client ms |
| --- | ---: | ---: |
| Revenue | 2003 (timeout) | 1448 |
| Medical activities | 1066 | 881 |
| Refund after 30 days | 758 | 961 |

Preparatory models-list reads took 990–1184 ms outside request latency. Results
were mixed; stochastic plan output also differed on the refund pair. This is
not sufficient evidence for broad enablement or a guaranteed latency saving.
No production customer transcript or audio was used in this benchmark.

## Recognition investigation

Same QA synthetic PCM, same configured U3 model, language/recognition prompt and
semantic-medium settings. Provider session echo verified the requested settings.
No generated replies, automatic response, manual end-turn shortcut or saved
configuration changes. The earlier high-eagerness configuration remains rejected
because it split the leadership question into separate final utterances.

| Fixture | First partial relative to fixture end ms | Final relative to fixture end ms |
| --- | ---: | ---: |
| Chairman | -1783 | 1679 |
| Leadership list | -2368 | 1637 |
| Paused person/company | -2612 | -1617 and 784 (two segments) |

Negative values mean the event arrived while the synthetic fixture was still
being streamed. Fixture duration includes its trailing silence. The first partial
is not proof that the complete question was available at that point. Provider
speech-stopped and final events were within 0 ms at rounded resolution. Thus
the measured delay is before finalization, not a VAV handler waiting after it.
Early partials may support speculative read-only preparation, but cannot safely
be promoted to complete caller intent without a separate quality evaluation.
Production endpointing remains unchanged; this candidate does not fix that delay.

## Validation

Full backend suite: **1528 passed, 31 skipped**, 187.31 seconds. Focused suite:
162 passed. Ruff lint and formatting passed, 248 files. Tests cover same-key
reuse, changed credentials, missing credentials, cancellation, prewarm failure,
nonblocking foreground fallback, isolation between calls, idempotent cleanup,
metadata privacy and unchanged scoped knowledge-repair evidence.

Fresh production baseline: `17c54e1b-439d-593d-abf5-7efae5e0ad8b`, completed,
105 seconds, nine response samples. P50 1051 ms, P90/P95 3323 ms, greeting 700 ms.
Revenue recovery timed out at 2052 ms; its entire response took 3323 ms and
correctly reported inability to resolve rather than inventing revenue. Existing
chairman/year/phone/correction/repeat/farewell behaviors were observed. Synthetic
fixtures were regenerated after the prior API deployment and reused byte-for-byte
for this round's candidate; do not compare them as identical to last round's PCM.

Candidate call `e980f8e3-db7e-514b-9412-d195ad20cd5b`, completed in 101 seconds.
Confirmation `06967854-b9ca-5f2b-b674-63a0a4852816`, completed in 102 seconds.
Each has nine measured responses and matching PCM hashes against the fresh
baseline. Both retained chairman/year answers, interrupted phone lookup, slow
digits, company correction and farewell. Unsupported revenue was refused without
an interpretation timeout. The request ledger records seven answered/one unresolved
in both candidates, versus six/one in the timed-out baseline. This is not proof
that all product conversations or all knowledge bases pass.

Preparation completed in 1400/1401 ms during greeting/early conversation and the
prepared client was used twice in each candidate. The provider split the revenue
fixture into two final utterances in both candidates, versus one in the baseline.
Thus this is not a clean causal estimate of connection savings: transcript
segmentation and model timing varied. Prior successful unmodified recovery turns
were also around 2.1 seconds overall. The baseline timeout must not be presented
as the typical baseline or as a guaranteed savings percentage.

Warmup itself generates no model tokens. Existing recovery made two model requests
in the first candidate (1181 reported input/28 output tokens), versus one timed-out
request with unknown usage in the baseline. No per-call cost saving is claimed;
provider usage after timeouts must be reconciled, not recorded as zero.

The confirmation SSH runner returned exit 1 after emitting AUDIO_COMPLETE; its
full audio/transcript observations and the persisted completed call were verified
separately, and no QA call remained active. Do not represent that shell exit as
a clean harness exit. No further calls are planned for this round.

Decision: retain only the opt-in QA canary, not broad rollout. The major unresolved
delay is provider finalization, now 1.7–1.9 seconds on the slow questions. Early
partials are available, but replacing finalization with aggressive cutoff or
guessing completion would undo the incomplete-speech protections. Any partial
preparation/turn-completion change requires its own isolated replay evaluation.
Sub-600 ms overall latency is NOT achieved. These are server measurements, not
browser speaker/mouth-to-ear measurements; no subjective recording review or SIP
test was performed.
